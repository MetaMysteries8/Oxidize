# Measure the integrated workflow

Choose representative workloads before implementation. Record hardware/runtime/toolchain, warm-up policy, sample count, median, and variability. Include bridge overhead and data conversion. Avoid comparing a Python wrapper against a disconnected Rust microbenchmark.

The CLI measures warmed batches through the actual Python interface with nanosecond monotonic timing and reports raw samples, median, and median absolute deviation. Correctness observation and timing use separate processes and disposable copies, and each timed invocation reconstructs fresh inputs. Input reconstruction is included; both sides use the same reconstruction policy. Component timing measures the component workload, not total application speed; use `oxidize workloads` for whole-application figures. Interleaving reduces bias from machine load and thermal drift but doesn't remove contention from other work. Repeat independently before drawing production conclusions.

Reject failures of correctness regardless of speed. A lower minimum_speedup may deliberately allow a measured regression, but document that policy. Oxidize (v0.2.0+) interleaves original/candidate rounds, keeps raw samples, requires the slowest round to clear `minimum_speedup`, and reports noisy or malformed timings as "no speed claim" (`performance.rounds`, `max_relative_mad`). `oxidize workloads` times whole-application commands on the original and the accepted workspace, with wall time and, on Linux/macOS, CPU time and peak RSS. Ranges are min/max over rounds, not statistical confidence intervals. Allocations and bridge-only overhead are still not measured.
